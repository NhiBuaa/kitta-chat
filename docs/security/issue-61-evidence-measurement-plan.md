| Class | Meaning | Allowed action in this planning step |

Existing metrics are route-level: `kittachat_http_requests_total` and duration use method, route template and status class. Existing request logs contain request ID, method, path, status, latency and sometimes verified `userId`. Existing Redis metrics contain operation/outcome counters, not limiter evaluator latency or actor/target dimensions. No raw IP, email, username, token, conversation ID, callee ID, file ID or call ID may be exported for this plan.

Class A means that an evidence source does not require a runtime change. It does not authorize access to retained production data. Retained production logs, metrics or deployment records may be inspected only after explicit access approval and only when the provenance contract below can be satisfied.

## Evidence-quality invariants

### Observation and censoring provenance

- Every evidence source or measurement row must identify its observation point in the request or event path, the upstream controls that may already have rejected or shaped traffic, and the population that the observation represents.
- Relevant layers are: client -> Nginx/edge limit -> body/parser limits -> current process-local limiter -> authentication/middleware -> route/controller -> downstream dependency. A row may omit a layer only when that layer does not apply.
- When metrics or logs are collected from the backend, the HTTP metrics and request-logging middleware start after Nginx and before the JSON parser and route middleware. Controller, query, queue and downstream evidence is collected later and therefore excludes requests rejected by parser, authentication or earlier route limiters. The row must state which of these populations it uses.
- Backend auth metrics observed after Nginx do not represent unconstrained client auth demand. Route/controller evidence does not include requests rejected by an upstream edge control, parser or earlier limiter.
- Invalid JSON and bodies rejected as too large do not reach route/controller observations. Traffic observed after the current process-local limiter is censored by the limiter being evaluated for replacement.
- Current Nginx behavior must be named when relevant: `/api/auth/` is shaped by `auth_limit`; other `/api/` traffic is shaped by `api_limit`; Socket.IO is subject to the connection control. The backend does not observe edge-rejected requests. Nginx has no `limit_req_status`, so current edge quota rejection uses the default `503` and cannot be inferred from backend `429` observations.
- Censored production observations cannot by themselves prove that a tighter candidate quota is compatibility-safe.

### Privacy-linkage feasibility

- Shared-NAT concurrency, per-user multi-tab/device cadence, refresh cadence by principal/session, target concentration, call multi-socket behavior and actor-level burst distributions require stable linkage across observations.
- Aggregate route/status/latency metrics cannot answer questions that require actor, target, resource, session or logical-attempt linkage.
- Linkage status must distinguish three meanings: **A — linkage required for final compatibility decision**, **B — linkage useful but not required for other aggregate evidence**, and **C — no actor linkage required for the named static/capacity/cost evidence**. A candidate may have A plus B or C when its final fairness decision and its cost evidence have different needs.
- `Blocked on approved privacy-preserving linkage design` applies only to the specific actor/session/target distribution or fairness claim classified A. It must not erase the decision value of aggregate latency, cost, throughput, error, queue, S3/presign, Redis-capacity or other evidence classified B or C.
- Technical desirability does not imply measurement feasibility. No raw IP, user ID, target ID, resource ID, credential or limiter HMAC/digest may be exported to make a measurement feasible.
- This planning step does not create an actor hash or HMAC and does not reuse the limiter HMAC design for telemetry. If aggregate telemetry cannot resolve a numeric candidate, the unresolved linkage is an approval blocker rather than permission to export identifiers.

### Retained-evidence provenance and freshness

- Retained logs, metrics and deployment evidence may support a numeric decision only when the evidence records, where available: deployed revision/release, observation dates and window, backend replica count, routing/load-balancing topology, Nginx limiter configuration, relevant environment overrides, Redis topology, route-affecting feature/config state, and known incident or degraded periods.
- Evidence with unknown or incomplete provenance may generate a hypothesis. It must not be used as compatibility proof.
- Existing tests prove tested semantics and contracts; they are not production-frequency evidence.
- Static source proves current repository behavior. It does not prove deployed traffic behavior unless the deployed revision is shown to match.

### Control-plane secret safety

- Provenance audit may read non-secret metadata such as revision/image digest, deployment timestamps, replica count, service/image names, routing topology, Redis topology, Nginx limiter/logging directives, retention configuration, timestamp basis and non-secret feature state.
- Secret, credential, API-key, token, password and private-key values must not be read, copied, logged or written to an audit artifact. Environment/config properties may be recorded only as `present`, `absent`, `unknown` or redacted metadata when required for provenance.
- If a control-plane interface cannot return required metadata without exposing a secret-bearing value or raw sensitive record, stop that source and classify it `requires additional authorization / unsafe metadata interface`.
- Artifact/build/log payloads must not be downloaded or opened only to search for provenance unless a later authorization explicitly permits that access.

### Temporal matched-window provenance

- Temporal matched-window applies only to retained runtime sources such as Nginx/backend logs or metrics, queue/email outcomes and Redis/runtime metrics.
- A retained-evidence window is eligible for later measurement only when the relevant runtime sources overlap the same observation interval and their timestamp basis/timezone is unambiguous.
- Major deployment or configuration changes inside the window must be partitioned or recorded. Known incident or degraded periods must not be silently mixed with normal periods.
- A runtime source pair with unknown overlap, ambiguous time basis or unpartitioned deployment/config/incident boundaries is `hypothesis-only`; it must not be used as compatibility proof.

### Revision and deployment binding

- Revision/deployment binding identifies the deployed SHA, image tag/digest and effective configuration/topology that produced a runtime dataset, and the matching repository source/tests that describe that behavior.
- Static source and tests prove semantics for their repository revision. They do not have a production observation window and must not be described as a temporal matched-window source.
- Workflow/build SHA is only a chain-of-custody candidate. It must not be called the deployed runtime SHA without an actual deployment/image binding.
- If revision binding is missing, runtime evidence cannot prove compatibility with current source. The runtime dataset and static source may still generate hypotheses when each limitation is explicit.

### Empirical workload and normative behavior

- Numeric approval must separate empirical evidence—frequency, burst, latency/cost, concurrency and retry patterns—from normative product/security requirements.
- Normative requirements include supported tabs/devices, recovery usability, redial/reconnect behavior, multipart part/retry behavior, administrator/group workflows, supported client choreography and accepted security tolerance for guessing or resource abuse.
- Historical traffic may include attackers, bots, client bugs, retry storms and degraded dependencies. Rare but legitimate behavior may be absent from the sample.
- `Production percentile + margin` alone is not sufficient numeric-policy justification. Measurement informs the decision; it does not define what product and security must support.
- `Governance approval required` and `normative product/security input materially required` are separate fields. Every final numeric policy requires explicit maintainer governance approval. Class D applies only when empirical evidence cannot define supported legitimate behavior or the security/fairness tradeoff; it must not be used as a synonym for final approval authority.

## Login semantic fingerprint

Source evidence is complete for current accounting:

- `server/src/middlewares/rateLimit.js` uses a process-local `Map` and key `String(req.ip || req.headers["x-forwarded-for"] || req.socket?.remoteAddress || "unknown")`. This is observed legacy behavior, not behavior to preserve.
- The first request starts a first-hit anchored fixed window. Later requests increment `count`; `resetAt` is not extended.
- The login limiter is mounted before the controller. Successful login, invalid user, Google-provider account, invalid password and controller failures all occur after admission and therefore consume the current counter.
- Requests over the limit increment `count` before returning `429`; rejected requests do not extend the window.
- `express.json({ limit: "10kb" })` runs before `/api/auth`; invalid JSON returns `400 BAD_JSON` and oversized bodies return `413 PAYLOAD_TOO_LARGE` without reaching the login limiter.
- Valid JSON missing `email` reaches the limiter and can fail later at `email.trim()`; this is source evidence, not a dedicated test case.
- No `skipSuccessfulRequests`, refund, result-aware decrement or equivalent exists.
- Current `429` has `Retry-After = max(1, ceil((resetAt-now)/1000))`, code `RATE_LIMITED`, login message and request ID. There is no body retry field or multi-bucket maximum-wait calculation.

The legacy key fallback is intentionally outside the compatibility promise. The approved identity invariant forbids limiter parsing of raw `X-Forwarded-For`; the canonical network actor must come from `req.ip` after the trusted ingress topology is verified. The current key has no explicit IP canonicalization, and the `"unknown"` fallback can collapse unrelated callers into one actor. These are migration/security gaps, not semantics to preserve.

Keeping login `10/15 min` therefore has two separate approval parts:

- Semantics intentionally changed: process-local to Redis-shared coordination, first-hit fixed window to sliding window, and current route-reaching accounting to proposed admitted-attempt/all-or-none accounting.
- Legacy behavior intentionally not preserved: raw X-Forwarded-For fallback, uncanonicalized network identity and the shared `"unknown"` fallback.

The two approved metadata-only audits found no retained source that is currently provenance-qualified for later aggregate measurement.
